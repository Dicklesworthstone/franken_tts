# franken_tts iOS App Plan

An iPhone app that is the website playground, rebuilt with native UI: download the model
once, pick or clone a voice, type, synthesize on device, listen, share. The Rust engine is
the same one the CLI ships; nothing about the model pipeline forks.

## 1. Why the phone is a different machine than the Mac

The port's governing arithmetic is weight traffic: ≈1.65 GB touched per 80 ms frame at Q8,
so ≈20.7 GB/s streamed for 1× real time (plan §2.5). The two chips sit very differently
against that floor:

| | Mac Mini M4 Pro | iPhone A18 / A18 Pro |
|---|---|---|
| Memory bandwidth | ~273 GB/s | ~60 GB/s class (LPDDR5X) |
| Headroom over the 20.7 GB/s floor | ~13× | ~3× |
| RAM | 24–64 GB | 8 GB |
| Default per-app memory ceiling | n/a | ~3.3 GB (jetsam); more with the increased-memory entitlement |
| Performance cores | 8–10 P | 2 P + 4 E |
| Sustained load | fan | passive, throttles in minutes |

Consequences the design must absorb rather than discover:

- **Real time is plausible but unpromised.** 3× bandwidth headroom at a realistically
  achieved 30–50% of peak puts the phone near 1× real time. The app's copy uses the same
  honesty rule as the site: publish a measured figure after it is measured, and nothing
  before. No claim ships in v1 copy beyond "synthesizes on device".
- **Memory is the binding constraint, not compute.** The native engine memory-maps the
  1.31 GB artifact (iOS is Unix; the `native-mmap` path compiles as-is), so the artifact
  costs address space and page cache rather than jetsam-accounted heap. The hydrated
  tensors and codec still cost real heap. The app requests the
  `com.apple.developer.kernel.increased-memory-limit` entitlement, loads the engine only
  on first synthesis, and frees it on background when memory pressure warrants.
- **ISA is not a problem.** A18 has NEON, dotprod, and i8mm; the kernels' runtime
  detection (`is_aarch64_feature_detected!`, which std implements via `sysctlbyname` on
  Apple platforms) picks the same tiers as an M-series Mac. Zero new kernel work.
- **Accelerate exists on iOS.** The codec's BLAS route is gated on `target_os = "macos"`
  today; the plan extends the gate to iOS so the codec keeps the measured-fastest path.
  If that gate turns out to be load-bearing in some macOS-specific way, the packed-GEMM
  fallback is already the tested non-BLAS route and the app still works, slower.
- **Threads: five, not six.** The team's six-way default is the measured M4 Pro knee. On
  2P+4E, five partitions leave one E core for UI and audio. The Swift layer sets
  `FTTS_INT8_THREADS=5` via `setenv` before the first engine call; a later measured knee
  can change one constant.

## 2. Architecture

```
ios/FrankenTTS.xcodeproj  (generated by xcodegen from ios/project.yml)
  Sources/                SwiftUI app
  FttsCore.xcframework    built by ios/build-rust.sh
        └── libftts_ffi.a (aarch64-apple-ios, aarch64-apple-ios-sim) + ftts_ffi.h
crates/ftts-ffi           staticlib crate, C ABI, thin over ftts-cli's synth module
```

### 2.1 The FFI crate

`ftts-ffi` depends on the `ftts-cli` **library** target and calls the same functions the
CLI's `say` path calls — `ModelBundle::resolve`, `LoadedModel::load`,
`synth::synthesize` — so there is exactly one native loading/synthesis implementation in
the tree. Enrollment mirrors the wasm crate: mel features plus `SpeakerEncoder` (hydrated lazily
on first enroll), fed raw f32 PCM at 24 kHz from the microphone. The eighteen presets embed via
`include_bytes!` from `crates/ftts-cli/presets/`, the same files every other surface uses.

C ABI, deliberately small (all functions return 0/pointer on success, and
`ftts_last_error_message()` explains failures; strings are UTF-8, buffers are
caller-owned unless documented):

```c
typedef struct FttsEngine FttsEngine;
FttsEngine *ftts_engine_open(const char *model_dir);
void        ftts_engine_close(FttsEngine *);
const char *ftts_last_error_message(void);      // thread-local, valid until next call
const char *ftts_presets_json(void);            // static [{name, character}] JSON
int   ftts_preset_vector(const char *name, float out[1024]);
int   ftts_synthesize(FttsEngine *, const char *text,
                      const float *speaker, size_t speaker_len, uint64_t seed,
                      float **out_pcm, size_t *out_len);   // caller frees via ftts_pcm_free
void  ftts_pcm_free(float *pcm, size_t len);
int   ftts_enroll(FttsEngine *, const float *pcm, size_t len, float out[1024]);
```

Concurrency contract: the engine is not thread-safe; the Swift side owns it inside an
actor and serializes calls. There is no progress callback across the ABI in v1: the UI
shows elapsed time and a character-count-based estimate during synthesis, and says so,
rather than faking a percentage. A callback-based progress ABI is a v2 item. Panics cannot cross the FFI: the workspace release profile is
`panic = "abort"`, so a Rust panic terminates the process rather than unwinding into
Swift, which is the defined-behavior choice.

### 2.2 Model delivery

Same pinned GitHub release assets and digests as the website manifest. Swift downloader:

- `URLSession` download tasks, one file at a time, with progress and a rolling-window ETA
  (the site's consent-and-progress contract, ported).
- Resume via `HTTP Range` from the byte count already on disk, like the site's loader.
- SHA-256 with CryptoKit, streamed over the file after download; a mismatch deletes and
  refuses, naming the file.
- Storage in Application Support, marked `isExcludedFromBackup` (2 GB does not belong in
  iCloud backups), with a Clear Model button reporting bytes freed.
- Explicit consent screen before the first download stating the size and that it stays
  on device — verbatim policy from the site.
- The asset names, byte sizes, and SHA-256 digests are duplicated into Swift as
  constants with a comment naming `site/model-manifest.js` as the source of truth; the
  two must move together when the model release is ever re-pinned.
- Sharing produces a WAV written by a small Swift RIFF writer from the returned PCM
  (16-bit, mono, 24 kHz — the same layout the CLI writes).

### 2.3 UI (SwiftUI, monster-themed)

One scrolling laboratory screen, matching the site's structure so the two playgrounds
feel like siblings:

1. **Header**: bolted "F" mark, FrankenTTS wordmark, VOICE_ALIVE tag, emerald-on-black.
2. **The Specimen** (model card): consent → download progress (per-file, bytes, ETA) →
   "loaded" state with storage used and Clear.
3. **The Voice**: preset cards (name + one-line character), "your voice" card opening the
   enrollment sheet: shows the Stella+Rainbow script, records via `AVAudioEngine`
   (mono float, resampled to 24 kHz), names the clone, runs `ftts_enroll`.
4. **The Utterance**: text editor (50,000 chars, counter), seed field with dice, Synthesize
   button with progress, waveform rendering of the result (SwiftUI `Canvas`), playback
   via `AVAudioPlayer`, compact audio/video sharing, and a privacy-redacted recent-result
   history retaining the newest 12 clips for up to seven days.
5. Footer: version, link to the site.

Theme: dark emerald (#020a06 background family, emerald accents), stitched-panel corners
via a small `BoltCorners` overlay view, JetBrains-adjacent monospaced accents using the
system monospaced font. Respect `accessibilityReduceMotion`; haptics on synthesis
completion. All controls get accessibility labels.

### 2.4 Audio session

`AVAudioSession` category `.playback` normally; `.playAndRecord` only during enrollment.
Microphone permission string states the recording is processed on device into a 4 KB
voice vector and discarded, matching the site's promise.

## 3. Memory budget (the load-bearing table)

| Resident item | Estimate |
|---|---|
| Hydrated int8 talker+microdecoder | ~0.8 GB |
| Codec (BF16 → f32 widened) | ~1.3 GB |
| Tokenizer + tables + working buffers | ~0.2 GB |
| Artifact via mmap | page cache, not app heap |
| **Heap total during synthesis** | **~2.3 GB** |

Under the ~3.3 GB default ceiling this fits but leaves little; with the increased-memory
entitlement (8 GB devices) it is comfortable. Mitigations in v1: engine loads on first
synthesis rather than at launch; the engine is dropped on `didReceiveMemoryWarning` and
on backgrounding when not mid-synthesis; the download path never holds more than one
chunk in memory. Devices below 6 GB RAM get a pre-load warning rather than a crash: the
app checks `ProcessInfo.physicalMemory` and says plainly that the model needs a recent
Pro-class device.

## 4. What is deliberately NOT in v1

- No streaming playback (synthesis completes, then plays — same as the site).
- No background synthesis; the app must stay foreground during a run.
- No App Store submission work (signing, screenshots, review copy) — the deliverable is
  a building, runnable Xcode project in-tree.
- No Metal: CPU-only, same as everywhere else in this project.

## 5. Verification

- `cargo check/clippy/test` for `ftts-ffi` on the host target; unit tests cover the
  error-path contract and preset table without the model, plus a model-gated
  smoke (open → synthesize "Hi." → close) on the host.
- `cargo build --release --target aarch64-apple-ios[-sim]` both green.
- `xcodebuild -project ios/FrankenTTS.xcodeproj -scheme FrankenTTS -sdk iphonesimulator`
  builds green. (Running with the 2 GB model in the simulator is a manual step,
  documented in ios/README.md.)
- On-device measurement of real-time factor is future work and gates any speed claim.

## 6. Risks, called out before implementation

1. **Jetsam on 6 GB devices.** Mitigated by the RAM check + copy; not fully solved.
2. **The Accelerate gate widening** could disturb macOS codec parity if the gate secretly
   encodes something macOS-specific. Mitigation: gate change is one `cfg` line, tested by
   the existing codec parity suite on macOS, and iOS falls back to packed GEMM if reverted.
3. **Thermal throttling** may halve throughput mid-paragraph. No mitigation in v1 beyond
   honest copy; the measured figure will be a sustained one.
4. **`ftts-cli` as a dependency** drags clap/symphonia into the app binary (~ a few MB).
   Accepted for v1 to keep one loading implementation; a later slimming can feature-gate
   the CLI surface out.
